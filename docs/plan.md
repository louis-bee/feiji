# 我们的恋爱网站：设计与实施方案

日期：2026-09-30  
状态：用户已授权按计划开发，当前实现四个核心页面；不执行远程部署。下文保留设计依据，运行方式与实际交付以 [README](../README.md) 为准。

实现取舍：Vue 3＋TypeScript＋Fastify＋SQLite；业务时区先设 `Asia/Shanghai`，可在设置修改；暂不加入回复、愿望、歌曲卡、标签等扩展。月历与图片查看采用轻量自建组件，日期采用经过测试的原生 Intl 与纯日期函数，而非强制引入候选 UI/日期库。

开源与官方资料依据见 [research.md](research.md)。

## 1. 一页结论

建议把它做成一个**手机优先的双人生活手账**，不是功能很多的情侣社交平台。

- **核心体验：** 打开就看到“今天是我们在一起的第 N 天”，能快速写下今天、回看照片、知道下一个重要日子。
- **页面：** 首页、恋爱日历、精选相册、纪念日；设置放在次级入口。
- **视觉已选：** [A 双人飞行日志](design-options.md)，以温暖旅行摄影手账为主，不默认混入其他整套风格。具体布局尚待内容方案确认。
- **内容提案：** [网站内容方案](content-plan.md)细化首页、日历留言、相册、生日周年及兴趣内容；回复、愿望与歌曲卡仍是待选扩展。
- **推荐技术：** Vue 3＋TypeScript＋Vite＋Vue Router；Node.js/Fastify＋SQLite；本地图片与视频文件；已有服务器反向代理提供 HTTPS。技术栈尚待确认。
- **已定登录体验：** 选两人的昵称之一，前端对写死的共用密码做简单校验。不实现后端认证；这只是页面入口门槛，不保证内容仅两人可见。
- **媒体范围：** 一期支持普通图片与视频，不提供原片下载；暂不设业务容量指标，不规划扩容或额外存储服务。
- **部署策略：** 沿用现有阿里云 2GB 轻量服务器；在开发机或 CI 构建前端，服务器提供静态资源和单进程 API。
- **开发预算：** 按基础视频播放、不含转码和备份的一期，暂估 9～14 个有效人日；待目标手机样片验证后修订，不是工期承诺。

## 3. 产品信息架构

### 3.1 页面与访问路径

| 页面 | 内容 | 核心操作 |
| --- | --- | --- |
| 登录 | 两个昵称/头像选项、一个密码输入框 | 选身份、进入；保留清晰错误反馈 |
| 首页 | 主照片、在一起天数、最近一个纪念日/生日、最近记录、3～6 张精选照片 | 记下今天、打开最近记录、查看相册 |
| 恋爱日历 | 月视图、日期标记、选中日记录列表 | 切月、回今天、补记、编辑、删除自己的记录 |
| 精选相册 | 图片/视频混合展示，手动精选与排序，按相册/月份浏览 | 上传、写说明、关联日期、打开大图/播放视频、设为精选 |
| 纪念日 | 下一次发生日、倒计时、年度/一次性分类 | 新建、编辑、置顶、生日设置 |
| 设置 | 昵称、头像、恋爱起始日、时区、退出入口 | 修改共同配置；不做复杂后台 |

移动端底部四项导航：首页 / 日历 / 相册 / 纪念日；PC 使用顶部导航与更宽的内容区，不仅把手机版等比例放大。编辑工具直接嵌入页面，不另做一套后台管理系统。

### 3.2 恋爱日历：先做好长期记录

- 一天可有多条记录，两人各自署名；同一天允许各写各的，不采用每天唯一一篇的覆盖模型。
- MVP 使用纯文本、图片/视频附件、可选简短标题；暂不做富文本编辑器、公开评论和多级回复。
- 月视图只显示简洁标记：有记录、有媒体、重要日子；格子内不播放视频。
- 点日期后，手机在下方/抽屉显示记录，PC 在右侧显示记录。没有内容时显示“为这一天留一句话”。
- 可补记过去的日期；记录日期与实际创建时间分开保存，不仅按创建时间归档。
- 默认 UI 只展示当前所选身份的编辑入口，相册与纪念日共同维护。这只是防误操作约定；前端身份可修改，不是真实身份或权限隔离。
- 保存失败时不清空编辑框；媒体上传未完成不能假装保存成功。页面离开时提示未保存内容。
- 两人同时编辑同一共享条目时做版本检查，冲突提示刷新或另存，不静默覆盖。
- 二期再考虑对记录回复、搜索、“去年的今天”、心情标签，不扩展成即时聊天系统。

### 3.3 精选相册：图片与视频共同记录

- 首页呈现人工精选照片或视频封面，视频不自动播放。
- 相册可按“约会 / 旅行 / 日常”等名称组织；一项媒体可关联日历记录，并被一个相册收录。
- 图片与视频混排；视频卡片显示播放标记和可获取的时长，封面不可用时有占位，不让整个列表预加载视频。
- 图片使用灯箱；视频使用独立原生播放器，不把 PhotoSwipe 或 sharp 当作视频处理库。
- 手机支持触摸、行内播放和横竖屏；PC 支持鼠标、键盘及合适的大图/视频展示宽度。
- 上传提供进度、取消、失败重试、批次结果；单个文件失败不要求全部重传。
- 文件落盘成功后再标为可用；用户删除操作需确认，关联媒体不能误删。暂不规划自动定期清理。
- **不提供原片下载按钮或专用下载接口。** 浏览器为了展示/播放仍会获取媒体字节，隐藏下载按钮不是防下载措施。
- 不承诺原片归档、自动备份或自动删除原始上传文件；这些均不在本期已确认范围。

### 3.4 纪念日与生日

- 区分一次性事件（某次旅行出发日）与每年重复事件（生日、恋爱周年）。
- 纪念日卡片显示事件名、下一次日期、距离天数；当天显示“就是今天”，不显示“还有 0 天”。
- 排序依据下一次发生日，不按原始年份排序。生日不应在今年已过后显示负数倒计时。
- 已结束的一次性事件移到过去事件区，不自动变成年度事件。
- 100 / 365 / 1000 天可以作为里程碑，但“365 天”和“周年”不能混为一谈，闰年会产生差别。
- 一期建议只做站内倒计时，不做邮件、微信或浏览器通知；网页倒计时本身不会主动推送提醒。

## 5. 技术架构与取舍

### 5.1 推荐结构

浏览器中的 Vue SPA（前端密码入口）→ 同域 HTTPS 反向代理 → 静态资源 / `/api/*` / `/media/*` → 单个 Node.js API → SQLite 与媒体文件目录。

- Vue 3＋TypeScript＋Vite＋Vue Router；API 负责跨设备持久化，并非因为前端校验就取消后端。
- 状态管理先用组合式函数；确有跨页复杂度时再引入 Pinia。
- 日期用 Day.js 的 UTC/Timezone 插件；日历候选 VCalendar；图片浏览候选 PhotoSwipe，视频用原生 HTML 播放器。
- API 使用 Fastify 5 路线，JSON Schema 校验入参，插件版本配套锁定。
- SQLite 驱动候选 `better-sqlite3`；参数化 SQL＋编号迁移，不先引入 ORM；避免同步长查询阻塞请求。
- 图片处理候选 sharp；视频流式落盘和读取，不把媒体 base64 存数据库，也不把整个视频读入内存。
- 没有 SEO、即时聊天需求，不引入 SSR 或 WebSocket。
- 单 API 进程、一个数据库文件，事务与 busy timeout 处理双人写入。若启用 WAL，未来备份时必须使用一致快照；备份当前不实施。

### 5.2 为什么不是更重的方案

- MySQL/PostgreSQL：当前不需要多实例写入，先不增加常驻服务。
- Redis：无分布式会话、队列需求。
- Docker：可选，若已有容器部署就沿用，否则 systemd 更直接。
- PocketBase：是另一条后端路线；内置认证不是当前前端入口的必需品，不与自建 API 混搭。
- 仅静态网页＋localStorage：无法实现两人的多台设备共享记录和媒体；localStorage 不能代替业务数据库。

### 5.3 已定：前端固定密码简单校验

1. 入口提供两个昵称选项和同一个固定密码。前端比较通过后进入页面，路由守卫只做 UI 拦截。
2. 建议用 `sessionStorage` 保存当前标签页的通过标记和所选 `actor_id`；刷新保留，退出清除。是否长期记住入口状态可以以后调整，不做后端 Cookie/会话。
3. 两个固定 `actor_id` 用来署名，昵称不是数据库主键；后端仅检查 ID 是否属于允许值，不声称验证了真实身份。
4. 不新增 `/api/session` 或服务端密码校验，不做注册、找回密码、第三方登录或角色系统。
5. HTTPS、参数校验、路径约束和上传错误处理仍保留，用于传输与程序正确性，不等于用户鉴权。

**明确的功能边界：**

- 前端资源可被下载，密码或比较逻辑可被找到；混淆、哈希、构建时环境变量都不能把前端校验变成可靠认证。
- 通过标记和身份可以被修改，路由守卫可以绕过；在没有其他访问控制时，API 可被直接读写，媒体链接可被直接访问，包括上传和删除操作的滥用风险。
- 退出只清理本地界面状态，不撤销 API 或媒体访问权限；不以“退出后外部无法访问”作为验收标准。
- `robots.txt`、不展示链接、随机媒体 ID、关闭目录索引和隐藏下载按钮均不保证私密。

按用户决定采用此简化方案，不再将后端认证列为待批准事项；同时不再描述为“技术上仅两人可见的私密网站”。如果以后要真正限制访问，再单独增加服务端或网关校验。

## 6. 数据与接口草案

此节是概念设计，不是已创建的数据库或 API。

### 6.1 数据模型

| 表 | 主要字段 | 规则 |
| --- | --- | --- |
| `settings` | 恋爱起始日、业务时区、天数口径 | 单站配置；入口密码只在前端配置，不建服务端认证数据 |
| `profiles` | 固定 ID、昵称、头像、公历生日 | 两条记录：飞机 `2006-10-25`、大黄丰 `2004-08-11`；昵称可改，固定 ID 不变 |
| `entries` | ID、记录日期、作者 ID、正文、创建/更新时间、版本号、删除时间 | 同一天多条；日期索引；作者为客户端所选身份，不保证真实性 |
| `media` | ID、上传者、类型 image/video、存储键、原文件名、MIME、宽高、字节数、视频时长/编码、可选封面键、状态、删除时间 | 视频专有字段可空；由后端生成路径，不返回磁盘绝对路径 |
| `entry_media` | 记录 ID、媒体 ID、顺序 | 图片与视频统一排序，校验关联是否存在 |
| `albums` | ID、名称、描述、封面媒体 ID、顺序 | 可先只建一个默认相册 |
| `album_media` | 相册 ID、媒体 ID、记录日期、说明、顺序、精选标记 | 一期每项媒体至多属于一个相册，可同时被日历引用 |
| `events` | ID、标题、类别、公历原始日期、重复规则、可选闰日策略、置顶 | 只做公历；一次性事件与每年重复事件分开 |

纯日期存 `YYYY-MM-DD`，用户已给出生日年份，不将其丢弃；创建时间存 UTC 时间戳。展示按配置时区，删除共享媒体前检查引用。

记录和关联更新使用事务；共享条目带版本号，不匹配返回冲突。记录日期、事件类型、相册关联建立索引。

### 6.2 API 分组

| 接口组 | 示例职责 |
| --- | --- |
| `/api/settings`、`/api/profiles` | 共同设置、两个昵称和生日 |
| `/api/entries` | 月摘要、按日读取、记录增删改 |
| `/api/albums`、`/api/media` | 相册、图片/视频元数据、排序、说明、精选标记 |
| `/api/events` | 纪念日维护、下一次发生日期 |
| `/api/uploads` | 图片与视频流式上传、处理结果、失败反馈 |
| `/media/:id/:variant` | 图片缩略图/浏览图、视频封面/播放文件；视频支持 HEAD 与 Range 请求；无原片下载专用接口 |

入口校验和退出由前端完成，没有 `/api/session`。API 使用统一错误、有限分页、参数白名单；正文按文本渲染，不允许任意 HTML。无后端身份验证时，这些 API 与媒体路径不具备用户访问权限限制，CORS/Origin 校验也不能阻止外部客户端直接调用。

## 7. 媒体、日期与服务器的关键细节

### 7.1 图片与视频策略

**范围已定，具体兼容参数是建议，不把“暂不考虑大小”理解成硬件和网络无限制。**

- 图片兼容目标：JPEG、PNG、WebP，GIF 直接展示时保留动画；HEIC、Live Photo 不承诺自动转换，需看实际样片。
- 可生成缩略图和浏览图，先校正方向；参数在视觉实施时选取。sharp 默认移除 EXIF 等元数据，仅对处理后的输出成立，不保证所有源文件脱敏。
- 视频兼容目标：MP4 容器＋H.264 视频＋AAC 音频（或无音轨）。MP4 后缀不保证内部编码一致，MOV/HEVC 等需单独验证，不以改扩展名代替转码。
- 一期建议不做服务端转码、HLS、自适应清晰度或第三方视频云。兼容性检测失败时明确提示重新导出兼容格式，不假装上传成功即可在另一台手机播放。
- 采用原生 `video` 的 controls、playsinline，用户点击播放，不自动播放；列表显示封面或占位，播放器按需加载。PhotoSwipe 只负责图片。
- 媒体信息可通过轻量探测读取；若需 ffprobe，仅用来检查容器、编码、时长等，不默认增加持续转码服务。播放器错误也要有可理解的提示。
- 播放文件通过支持 Range 的标准文件服务输出，验证 HEAD、206、Content-Range 及无效范围的 416；不手写不完整的分段读取实现。
- 视频流式上传/落盘/读取，避免整段读入内存；先整文件重试，不默认实现分片上传或断点续传。支持播放 Range 不等于支持断点上传。
- 当前不确定单文件业务限额、总空间配额或扩容预算，移除原 15MB/10 张预设。实现时检查代理/上传库默认限制与超时并协调，资源不足应明确失败，不能承诺任意大小均可上传。
- 所有媒体存现有服务器，文件目录与应用产物分离，不开启目录索引，不把数据库放进静态目录；不开放目录索引仍不等于链接受保护。
- 不提供原片下载入口，不自动删除源文件。视频用于播放的文件仍必须保存，不因“无需下载原片”而删除。
- 列表懒加载、宽高占位，首屏主照片优先显示；不做媒体离线缓存。Cache-Control 可减少不期望的缓存，但不是鉴权。
- 图片处理初期串行；上传支持进度、取消、失败反馈，不引入 Redis 队列。

视频格式与 HTTP Range 的新增官方依据见 [调研补充](research.md#7-视频支持补充调研2026-09-30)。

### 7.2 日期规则

- 推荐固定业务时区 `Asia/Shanghai`，**待确认**；旅行时不随设备时区跳变。
- **已确认：公历，从 `2026-06-11` 开始，当天算第 1 天。** 页面统一用“在一起第 N 天”，计算为业务日期差＋1，不把日期口径改成累计飞行小时。
- 大黄丰生日 `2004-08-11`，飞机生日 `2006-10-25`；每年按公历月日重复，年份保留。
- 先将当前时间转换为业务时区的年月日，再计算日期序号差；不能直接把时间戳差除以 24 小时。
- 避免 `new Date('YYYY-MM-DD')` 的 UTC 解析与本地显示混用导致偏移。
- 年度事件目标日严格早于今天才滚动到下一年；当天显示“就是今天”。
- 两个已知生日不涉及 2 月 29 日；若以后新增该日期的年度事件，再要求选择平年策略，不默认推断。
- 不引入农历换算库或农历设置。
- 手机休眠恢复、页面重新可见与跨午夜时重算；开始日若在未来，提示修正或显示距离开始天数。

### 7.3 沿用现有阿里云服务器

用户已确认现有 2GB 轻量服务器正常、能满足基本需求。本轮不排障、不扩容、不另选云平台，也不做媒体容量预算；这不是已经测试过无限大小文件的承诺。

实施时仅保留轻量化约定：

- 前端在开发机或 CI 构建，线上不长期运行 Vite 开发/预览服务器。
- 单 API 进程，媒体流式读写，图片受限并发，不在 2GB 机器上默认跑视频转码。
- `better-sqlite3`、sharp 等原生依赖按目标系统和 CPU 安装，不能上传 macOS 的 `node_modules` 当作 Linux 依赖。
- 未来有实际容量需求再加存储，只让媒体存储逻辑集中管理，不提前引入对象存储适配层。
- 实现时处理磁盘不足、超时和部分上传文件，避免错误成功提示；不把暂缓容量规划变成忽略异常。

## 8. Web 部署与 Android 应用路线

实施顺序已明确：**先完成 Web 正式部署和双方真实浏览器使用，再制作 Android WebView 薄壳。**完整步骤、风险门槛、原生文件选择、视频全屏、返回键、错误页、签名与设备验收见 [Web 上线与 Android 封装计划](android-app-plan.md)。

### Web 部署

1. 用户提供拟使用的域名/子域名，并在实际操作前确认服务器系统、架构、磁盘、现有代理和端口；复用 Nginx/Caddy，不重复占用 80/443。
2. 在服务器重新安装匹配 Linux 与 CPU 的锁定依赖并构建，不复制 macOS 的 `node_modules`，不在线运行 Vite 开发服务。
3. API 绑定回环地址，通过正式域名 HTTPS 代理；持久 `DATA_DIR` 使用发布目录外的绝对路径，更新代码不覆盖数据库和媒体。
4. 低权限用户运行单服务，交给 systemd 或已有进程管理器；HTTP 跳转 HTTPS，代理保持视频 Range。
5. 电脑、双方手机普通浏览器验收入口、日历、上传、视频拖动、两设备同步、重启持久化和移动布局。
6. 公网部署前再次确认前端口令风险：保持现状需接受 API/媒体可被绕过访问；若改变为服务端/网关校验，作为单独需求处理。

### Android WebView 薄壳

1. 只有正式 HTTPS Web 稳定后才创建 `android/` 工程，固定正式域名；浏览器访问方式不变。
2. 使用无 ActionBar 的单 Activity WebView，保留系统状态栏；站内域名留在 WebView，外链交给系统浏览器，明文 HTTP 和未知协议默认拒绝。
3. 接入 HTML 文件多选、取消回调、原生视频全屏、WebView 历史返回、错误/重试页和 Activity 状态恢复；首版不开放通用 JS 桥，不加入相机直拍、通知或离线写入。
4. 双方真实 Android 手机验收上传、视频、返回键、前后台、弱网、刘海与手势导航；先生成签名 release APK 侧载，应用商店和 TWA 后置。
5. 网页业务更新通常只发布 Web；域名、图标、文件选择、视频全屏和原生权限变化才需要更新 APK。

### 暂缓：备份、扩容和额外维护体系

- 按用户要求移出一期，不配置异机备份、备份周期、恢复演练、对象存储或付费服务。
- 不承诺 RPO/RTO，不把“存在服务器上”或“用了 Git”描述成已经备份；故障或误删可能无法恢复。
- 若以后启用备份，应同时覆盖数据库和媒体，并使用 SQLite 一致快照，而非直接复制正在写入的数据库。相关技术资料保留在调研文档，不是当前任务。
- 不创建定时任务或自动化；新增维护功能时再确认范围。

### 必测清单

- 日期：开始当天为第 1 天、开始前、月末、跨年、两个生日当天及已过生日、业务时区、页面过午夜。
- 入口：错误密码、缺少身份、刷新、退出、直接打开页面路由；文档明确本地标记和 API 可绕过，不以“匿名不能访问”为本期验收。
- API：非法日期、非法作者 ID、超长文本、越界分页、不存在的媒体关联被拒绝；合法作者 ID 只是署名，不是身份验证。
- 图片：竖图方向、透明 PNG、GIF、解码失败、重复上传、网络中断、磁盘不足、删除仍被引用的媒体。
- 视频：双方手机和 PC 实测播放/声音/暂停/拖动/行内与全屏，验证 206/416、取消上传、不兼容编码提示；列表不自动播放或加载全部视频。
- 响应式：360～430px 手机、平板宽度与 1280px 以上 PC；触摸、鼠标、键盘、横竖屏、键盘弹起、长昵称和错误反馈。
- 发布：Linux 原生依赖可用，停止重启仍有数据，更新不覆盖媒体；不含备份恢复验收或无损灾难恢复承诺。

### 二期候选，不预先承诺

“那年今天”、关键词搜索、愿望清单、旅行足迹、轻量回复、标准 PWA/TWA、手动导出纪念册。Android WebView 薄壳已经进入已规划路线，但必须排在 Web 正式上线和真实浏览器验证之后；其他功能只有核心记录习惯稳定后再加。

### 当前与后续工程目录

- `web/`：已实现的 Vue 前端，按首页、日历、相册、纪念日组织功能。

- `tests/`：日期、API 与桌面/模拟手机浏览器流程。

- `android/`：Web 正式上线并通过真实手机浏览器验收后再创建 WebView 工程，不提前写死临时域名。

Git 默认主分支 `main`；功能使用短分支。提交按可理解的功能组织，文档、迁移和代码一起维护；依赖锁文件应纳入版本控制。

本轮只初始化仓库，不修改全局 Git 配置、不擅自设置远程、不推送，也不自动提交。用户尚未明确要求创建提交；首次提交待确认。Git 保存的是代码与方案版本，**不是照片和数据库的备份系统**。
