## 1. 提供游客访问入口（只读，免口令） · 高优先级

**说明**：登录页新增「游客」入口，无需口令直接进入；游客只能查看，不能编辑任何内容、不能进入设置。当前口令仅为前端校验，API 本身无鉴权（见 README「访问边界」），因此要做到「真正不能编辑」需在服务端对游客做只读拦截，否则仅前端隐藏按钮可被绕过。

**要点**
- 前端：`store` 增加只读角色（如 `actor = "guest"`）；隐藏「记下今天」、编辑/删除按钮、相册上传、设置入口，并加页面级守卫拦截 `/settings`。
- 后端：写接口（entries/media/albums/events/settings 的 POST/PATCH/DELETE）在游客态下返回 403，只放行读接口（GET/bootstrap 等）。
- 边界确认：游客可看的内容是否与「双人」完全一致（含生日、恋爱起点等真实资料）需在文案上再次确认。

**难度**：中高。核心成本在后端只读拦截与前端各入口的逐点隐藏/守卫。
**时间**：2~3 天；若只做前端隐藏约 1 天，但存在被直接调 API 绕过的风险，不建议。

## 2. 定制 input 的 required 提示、confirm 组件 · 中优先级

**说明**：目前 9 处 `required` 走浏览器默认提示、8 处删除/离开用原生 `confirm()`，样式不统一且无法定制文案/按钮。改为统一的自定义校验提示与 Promise 化确认弹窗组件。

**要点**
- 定制 required：统一校验逻辑与错误文案（可用 `@invalid` / `setCustomValidity` 或自写校验），替换现有 9 处。
- confirm 组件：新增 `ConfirmDialog.vue`（Teleport 遮罩 + 确认/取消，支持危险样式与可选主按钮文案），以 Promise 形式调用；替换 `App.vue`、`EntryCard.vue`、`EntryEditor.vue`、`AlbumPage.vue`、`EventsPage.vue`、`SettingsPage.vue` 中的 8 处原生 `confirm`。

**难度**：中。逻辑清晰，主要是统一替换与组件封装。
**时间**：1~2 天。

## 3. 样式拆到组件内部 · 中低优先级

**说明**：`web/style.css` 约 3166 行，为全局样式。将其按归属拆到各组件/页面的 `<style scoped>` 或组件级样式块，降低维护与命名冲突成本。纯重构，无用户可见收益，建议在功能稳定后逐步进行。

**要点**
- 按 8 个组件 + 6 个页面逐个拆分，先处理大页面（Calendar/Album/Settings）再处理通用组件。
- 抽离真正全局的部分（变量、reset、按钮/图标等基础样式）保留在全局层。
- 每拆一个模块跑一次 `npm run typecheck` / `npm run build`，并人工过一遍对应页面，避免样式回归。

**难度**：中高（机械量大、类名归属易错、回归风险高）。
**时间**：2~4 天，建议分 3~4 批提交。

## 4. 上传真实图片记录数据（非开发） · 独立/持续

**说明**：非开发任务，属数据录入。将真实照片/视频与记录补进相册、日记、封面等。不依赖代码改动，可与上述开发并行进行。

**建议**：在「游客访问入口」上线前先录入一批基础内容，让游客有内容可看；封面、纪念日等关键资料优先补齐。

**难度**：无。
**时间**：约 0.5~1 天（取决于素材整理与上传量），可持续补充。
