# Web 上线与 Android WebView 封装计划

日期：2026-10-10  
状态：实施计划，尚未远程部署、创建 Android 工程、生成 APK/AAB 或发布应用。  
关联：[当前实现与运行说明](../README.md) · [整体实施方案](plan.md)

## 1. 结论：先让 Web 稳定上线，再做 Android 壳

**建议顺序：Web 完成真实手机验证 → 域名 HTTPS 正常上线 → 稳定使用一段时间 → 封装 Android WebView。**

原因不是 Android 壳很难，而是壳应用只负责显示已经存在的网站。若先做壳，会同时调试服务器、域名、移动网页、上传、视频和 Android WebView，难以判断问题来自哪一层。

先上线 Web 有这些收益：

1. 电脑、Android、iPhone 都能直接使用同一域名，不等待 APK。
2. 先验证真实服务器、磁盘、HTTPS、图片上传、视频 Range、两台设备同步和重启持久化。
3. Android 壳最终只固定加载一个已经验证的 HTTPS URL，原生工作量明显降低。
4. 后续大部分页面更新只需发布 Web，不必重新发 APK；只有壳层行为、图标、权限或签名变化时才更新 Android 包。
5. WebView 与普通浏览器共用同一套 API 和数据，但各自的本地入口状态并不保证共享。

Android 壳不应阻塞 Web 正常使用。即使以后停止维护 APK，域名网站仍然可以从普通浏览器打开。

## 2. 目标效果

首版选择 **无 ActionBar 的 Android WebView 薄壳**，不先做 TWA，也不把网页重写为原生界面。

正常打开后的结构：

```text
Android 系统状态栏（保留，颜色匹配暖纸白）
┌──────────────────────────┐
│ 双人飞行日志网站自己的顶部栏 │
│ 首页 / 日历 / 相册 / 纪念日  │
│ 日记、照片和视频内容          │
│ 网站自己的底部导航            │
└──────────────────────────┘
Android 手势导航区域
```

- 不显示浏览器地址栏、标签页、浏览器三点菜单。
- 不显示额外 Android 标题栏，避免和网站顶部栏重叠。
- 保留系统状态栏和底部手势安全区，不强行做刘海沉浸式。
- 站内链接留在 App；外部 `https` 链接交给系统浏览器；电话、地图等协议只有以后确有需求再允许。
- 网站不可访问时显示带“重试”和“用浏览器打开”的原生错误页，而不是空白屏。

## 4. 阶段 A：把 Web 正常部署到域名

### 4.1 部署前确认

不在仓库记录 SSH 密码、私钥或云控制台凭据。实际操作前确认：

- 阿里云轻量服务器的系统、CPU 架构、磁盘剩余量和现有 80/443 占用。
- 准备使用的域名或子域名，例如 `love.example.com`；具体值由用户提供。
- DNS 可修改，服务器安全组允许 80/443。
- 是否已有 Nginx 或 Caddy。存在时复用，不并行安装另一套代理争抢端口。
- Node.js 满足项目要求；原生依赖必须在服务器重新安装，不能上传 macOS 的 `node_modules`。

### 4.2 推荐生产结构

```text
公网 HTTPS 域名 :443
        ↓
Nginx / Caddy（TLS、请求转发、必要的上传超时）
        ↓
127.0.0.1:3001 Fastify
        ├── dist/                 生产 Web
        ├── /api/*                SQLite 业务接口
        └── /media/*              图片和视频 Range

独立持久目录
        ├── journal.sqlite
        ├── journal.sqlite-wal
        └── media/
```

- API 只监听回环地址，不直接暴露 3001 到公网。
- `DATA_DIR` 使用独立绝对路径，不能放在版本化发布目录里，避免更新代码覆盖数据。
- 应用使用专用低权限系统用户，由 systemd 或已有进程管理器守护；不叠加多个守护方案。
- 线上只运行构建结果和 API，不运行 Vite dev/preview server。
- 代理需支持视频 Range，不能把 `Range`、`206`、`Content-Range` 破坏掉。
- 上传大小仍按当前产品决定暂不设业务配额，但 Nginx/Caddy、超时、磁盘和客户端必然存在工程上限；部署时必须对齐代理与应用配置并明确失败提示。

### 4.3 HTTPS 与域名

- DNS 指向服务器公网 IP。
- 为域名签发并自动续期 TLS 证书。
- HTTP 统一跳转 HTTPS。
- 不允许 Android 使用明文 HTTP 作为正式地址；Android 清单保持禁止 cleartext traffic。
- 证书链需在目标 Android 手机的系统 WebView 中正常信任，不能只在开发电脑上验证。

### 4.4 上线前的访问边界决策

当前项目按既定需求只做**前端写死口令**，并明确不是真正认证。部署公网后：

- 口令可从前端资源中找到。
- API 和媒体 URL 可绕过页面入口直接访问、写入或删除。
- WebView 不会改善这个问题，它只是另一种网页入口。

因此上线前必须再次做知情确认：

1. **保持现状：** 接受公网地址泄漏后的风险，不在网站保存无法承受泄漏的内容；或
2. **增加最小服务端/网关访问校验：** 这会改变此前“仅前端校验”的决定，需要单独设计，不能悄悄追加。

本计划不擅自修改已确定的前端口令方案，但将其列为公网部署的明确风险门槛。

### 4.5 Web 上线验收

至少在电脑浏览器、双方 Android/手机浏览器各完整执行一次：

- 域名 HTTPS 正常，刷新子路由不会 404。
- 选择身份、输入口令、退出和重新打开行为符合预期。
- 新建、编辑、删除日历记录；两台设备能看到同一份数据。
- 上传实际手机照片、MP4/H.264/AAC 视频；图片方向正确，视频能播放、拖动、全屏。
- 大图、缩略图、视频 URL 全部为同一 HTTPS 域名，无 mixed content。
- 服务重启后数据库和媒体仍在；代码升级不覆盖持久目录。
- 磁盘不足、超时或不支持格式时有可理解错误，不出现假成功。
- PC 与 360～430px 手机布局无横向溢出，系统输入法弹起后仍能保存。

## 5. 阶段 B：先正常使用 Web

建议先用浏览器实际使用几天到一两周，而不是部署成功当天立即锁定 APK。

观察并记录：

- 是否经常被要求重新输入前端口令。当前使用 `sessionStorage`，新标签页、App 进程被杀或 WebView 重建后可能重新进入；这是现有行为，不应在壳层偷偷改变。
- 双方手机相机的真实图片与视频格式是否兼容。
- 上传速度、视频拖动、页面恢复、横竖屏和返回操作是否自然。
- 首页、日历、相册和纪念日的移动布局是否还要调整。
- 域名、证书和进程是否稳定。

只有网页本身稳定后，Android 壳才开始承担“应用入口”职责，而不是用原生代码掩盖 Web 问题。

## 6. 阶段 C：创建 Android WebView 薄壳

建议新建独立目录 `android/`，使用 Android Studio、Kotlin 与 AndroidX WebKit。Android 工程与 Web 工程可以放在同一仓库，但构建、版本号和发布记录分开。

### 6.1 创建前需要用户确认

| 配置 | 示例/说明 |
| --- | --- |
| 正式 HTTPS URL | 例如 `https://love.example.com/`，必须先真实可用 |
| 应用名称 | 建议“双人飞行日志” |
| applicationId | 例如个人反向域名 `com.example.ourflightlog`；发布后不应随意更改 |
| 最低 Android 版本 | 根据双方真实手机确定，不凭空假设；先列设备型号和系统版本 |
| 图标和启动图 | 使用原创飞机/企鹅/航迹元素，不直接复制腾讯/QQ 官方标识 |
| 分发方式 | 两人侧载 APK，还是提交应用商店；首版建议先侧载 |

### 6.2 Android 工程基础

- 单 Activity、无 ActionBar 主题。
- Manifest 只申请 `INTERNET`；文件选择优先使用系统 Storage Access Framework，不默认申请读取全部相册或存储权限。
- `usesCleartextTraffic=false`，仅加载 HTTPS 正式域名。
- WebView 启用 JavaScript、DOM storage 和 Cookie；不启用不必要的文件系统访问。
- 启用 Safe Browsing；禁用 WebView 调试的 release 构建，debug 构建可临时启用。
- **不添加 `addJavascriptInterface` 原生 JS 桥**。首版不需要，避免扩大攻击面。
- User-Agent 可附加简单 App 标记用于排查，但网页功能不能只对该标记开放。

### 6.3 导航白名单

- 仅正式域名及明确的同站子域留在 WebView。
- 站内 `http` 不允许；若误出现则拒绝或跳转 HTTPS。
- 外部 `https` 链接使用 `ACTION_VIEW` 交给默认浏览器。
- `intent:`、`file:`、`content:`、`javascript:` 等非普通站内导航默认拒绝；以后确有功能再逐项白名单。
- 弹窗和新窗口默认不在未知 WebView 中打开，转换为明确的外链行为。

### 6.4 图片和视频上传

当前网页使用 `<input type="file" multiple>`。Android 壳必须实现 `WebChromeClient.onShowFileChooser`：

- 读取网页请求的 MIME 类型和单选/多选模式。
- 调起系统文件/照片选择器，支持图片和视频多选。
- 用户完成后向 WebView 返回 `Uri[]`。
- 用户取消、按返回键或选择器异常时必须回调 `null`，否则网页可能永远认为仍在选择文件。
- 不默认加入直接拍照/录像。若以后增加，需要 FileProvider、相机 Intent、临时 URI 和相应权限流程，另行设计。
- 选择器只负责提供文件，上传进度、取消、格式错误仍由现有网页 UI 处理。

### 6.5 视频与全屏

- 使用 `WebChromeClient` 处理 HTML 视频的 `onShowCustomView` / `onHideCustomView`，让全屏视频正确覆盖网页并恢复。
- 验证 MP4/H.264/AAC 播放、暂停、拖动、全屏、返回退出全屏和屏幕旋转。
- WebView 内核能否播放某种 HEVC/MOV 仍取决于设备和系统，不因为封装成 App 就自动兼容。
- WebView 不做视频转码；格式不兼容时沿用网页错误提示。

### 6.6 返回键优先级

Android 返回/预测性返回按以下顺序处理：

1. 若正在视频全屏，退出全屏。
2. 若网页有已打开的对话框/媒体查看器，网页先关闭；为可靠协作可后续增加受控的 Web 消息，而不是开放通用 JS 桥。
3. 若 WebView 有站内历史，`goBack()`。
4. 已在首页时第一次返回提示“再按一次退出”，或按产品决定直接退到后台。

首版至少实现 1、3、4。网页弹窗目前使用 HTML `dialog`，需在真实 WebView 测试系统返回行为；若表现不可靠，再设计最小、单向且限定域名的通信机制。

### 6.7 生命周期与状态

- Activity 重建时保存/恢复 WebView 状态和导航历史，避免旋转屏幕回首页。
- App 切后台再回来尽量保留当前页面与未提交输入；进程被系统杀死后不承诺恢复所有草稿。
- 当前身份/入口状态在 `sessionStorage`。它与普通 Chrome 不共享，并可能随 WebView 会话消失；首版接受重新输入口令。
- 如果以后需要“打开 App 永远直接进入”，应单独确定本地记住策略；它仍不能替代服务端访问控制。
- Web 数据清理、App 卸载和浏览器清理互不等价，设置页需避免承诺它们共享状态。

### 6.8 加载、离线和错误页

- 启动时显示与 A 方案一致的原生 Splash，进入后才显示 WebView。
- 顶部可用极细加载进度或只保留启动态，不添加重复的原生标题栏。
- 无网络、DNS 错误、TLS 错误、5xx 和维护状态提供明确错误页与“重试”“用浏览器打开”。
- **TLS 证书错误不得无条件忽略继续加载。**
- 首版不声称支持离线记录。无网络时显示错误，而不是让用户写入一个无法同步的本地分叉版本。

## 7. 阶段 C 验收矩阵

使用双方真实 Android 手机，至少覆盖：

| 场景 | 验收 |
| --- | --- |
| 首次启动 | 无浏览器地址栏/标签头、无 Android ActionBar，状态栏颜色协调 |
| 入口 | 两个身份、正确/错误口令、退出、杀进程重开行为明确 |
| 导航 | 四个主页面、深链、刷新、返回键、首页退出、外链进浏览器 |
| 日历 | 新增、编辑、删除、补记、输入法弹起、未保存提示 |
| 图片 | 单选/多选、取消选择、上传进度、失败重试、查看和缩放 |
| 视频 | 选择、上传、播放、拖动、全屏、旋转、退出全屏、不兼容提示 |
| 生命周期 | 前后台切换、锁屏解锁、横竖屏、低内存后重开 |
| 网络 | 飞行模式、弱网、服务器停止、域名错误、证书异常、恢复后重试 |
| 设备适配 | 刘海/挖孔、三键导航/手势导航、系统深色模式、字体放大 |
| 数据一致性 | App 新增后 PC 浏览器可见；PC 修改后 App 刷新可见 |

这里的“飞行模式”指 Android 网络测试，不是网站内容功能。

## 8. 阶段 D：签名与分发

### 8.1 建议先侧载 APK

两人自用的首版可以生成 release APK，通过可信的私有渠道安装：

- 生成正式签名密钥，并设置稳定 `applicationId`、`versionCode`、`versionName`。
- 签名文件与密码不放 Git，不只保存在开发电脑唯一一份；至少保存一份安全副本。
- 在第二台手机测试“安装旧版 → 保留 App 本地状态升级新版”。服务器数据本身不随 APK 更新或卸载删除。
- Android 可能提示允许安装未知来源；这是侧载的正常系统流程，不应要求关闭其他系统安全保护。

### 8.2 应用商店后置

若以后要上 Google Play 或其他商店：

- 生成 AAB，按目标商店要求准备隐私说明、数据安全表单、截图、图标、内容分级和测试轨道。
- 简单 WebView 壳是否符合商店当时的最低功能/内容质量政策需要届时重新核查，不在本计划中保证审核通过。
- 商店签名与侧载签名策略要提前确定，避免同一 `applicationId` 因签名不一致不能覆盖安装。

## 9. Web 更新与 App 更新的边界

| 改动 | 只更新 Web | 需更新 Android 包 |
| --- | --- | --- |
| 页面样式、文案、日历和相册业务 | 是 | 否 |
| API、数据库迁移、媒体处理 | 是，同时部署服务器 | 否 |
| 正式域名变更 | 否 | **是**，同时改导航白名单与配置 |
| App 图标、启动图、应用名称 | 否 | 是 |
| 文件选择、返回键、视频全屏逻辑 | 否 | 是 |
| 新增相机、通知、定位等原生权限 | Web 可能也改 | 是，并重新评估隐私 |
| Android SDK、WebView 兼容修复 | 否 | 是 |

因此正式域名最好在创建 Android release 包前稳定下来。测试域名可用于 debug 构建，但 release 不保留任意 URL 输入框，避免壳变成通用浏览器。

## 10. TWA 的后续位置

首版不采用 PWA＋TWA，但保留未来迁移可能：

- WebView：外壳控制强，无域名验证失败后出现浏览器工具栏的退化，最符合“固定网站浏览器”。
- TWA：由兼容浏览器呈现，需 HTTPS、Web App Manifest、Digital Asset Links、稳定签名与域名；验证失败或浏览器不支持时可能退到带工具栏的 Custom Tab。
- 若以后网站完成标准 PWA、希望上架并尽量沿用 Chrome 行为，可重新评估 TWA。业务页面和服务器无需重写，但 Android 工程与验证配置要调整。

## 11. 工作量判断

在 Web 已稳定部署的前提下：

| 工作 | 粗略量级 |
| --- | --- |
| 最薄的无标题栏壳、固定域名、基础导航 | 数小时到 1 天 |
| 文件多选、视频全屏、返回键、错误页、状态恢复 | 约 1～3 个有效人日 |
| 双方真实设备兼容修正、release 签名和升级验证 | 约 1～2 个有效人日 |
| 商店材料与审核修正 | 另计，取决于商店和当时政策 |

总计可按 **2～5 个有效人日**准备自用稳定版，前提是 Web 已在双方设备正常使用。若加入相机直拍、通知、离线写入、原生相册权限或服务端认证，需要重新估算。

## 12. 下一步执行顺序

1. 用户提供拟使用的正式域名/子域名，并确认服务器系统、架构、现有代理和端口。
2. 再次确认公网仍保持前端口令，还是改变为最小服务端/网关校验。
3. 编写部署配置，构建并在阿里云服务器启动，配置 DNS 与 HTTPS。
4. 双方用普通浏览器完成 Web 上线验收，使用一段时间并修正移动端问题。
5. 收集双方 Android 手机型号、系统版本，确认应用名、包名、图标和侧载/商店分发方式。
